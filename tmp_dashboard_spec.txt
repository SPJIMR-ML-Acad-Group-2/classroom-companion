Classroom Companion
Dashboard Tiles & Role Visibility Specification (Updated as per Latest Requirements)

1. Dashboard Architecture Philosophy
The system follows asingle-dashboard architecture:
All users land on the same dashboard layout.
Tiles are rendered dynamically based on user role.
No separate dashboards per role.
Backend enforces access validation.
Frontend only reflects permissions returned by backend.
Email ID is the primary identifier.
Role + permission mapping determines tile visibility and action rights.
This ensures scalability, modularity, and clean access governance.

4. Role-Based Access Philosophy
Access is determined by:
Role
Course mapping
Batch mapping
Explicit permission configuration
Access types:- Read- Write- Approve- Full Control
Role permissions are not hardcoded in UI.Permissions must be configurable via backend role-permission mapping table.

5. Program Office Dashboard Tiles
Tile 1: Onboard New Batch
Purpose:Create and initialize academic batches.
Capabilities:- Create batch (code, name, program type, start/end date)- Import students via Excel- Add students manually- View ongoing batches- View archived batches

Tile 2: Manage Batches
Purpose:Structure batches internally.
Capabilities:- View all batches- Create core divisions- Create specialization divisions- Create ACAD groups- Assign students to divisions- Modify division structure

Tile 3: Manage Courses
Purpose:Define and configure academic courses.
Capabilities:- Select batch- Create course (name, code, term, core/specialization)- Assign multiple faculty- Assign multiple divisions- Assign primary & secondary classroom coordinators- Session-wise faculty mapping

Tile 4: Timetable & Workload Management
A. Timetable
View divisions
Filter by batch
Add class events manually
Upload timetable via CSV
Map course, faculty, division, and time
B. Workload Analytics
Weekly class count per division
Faculty workload tracking
Week-over-week comparison

Tile 5: Attendance Hub
Purpose:Centralized attendance visibility.
Views:- Batch-wise- Division-wise- Course-wise- Student-wise
Capabilities:- Search & filter- Attendance percentage calculation- Low-attendance flagging

Tile 6: Student Concerns Hub
Purpose:Track student-raised issues.
Capabilities:- View concerns- Filter by batch/division/status- Update status (Open, In Progress, Resolved)- Add internal comments

Tile 7: Leave Request Hub
Purpose:Manage academic leave requests.
Capabilities:- View leave requests- Review dates, purpose, attachments- Approve / Reject- Track status

Tile 8: Change Access (Admin Only)
Purpose:Role and access governance.
Capabilities:- View all users- Modify roles- Approve access change requests- Grant/revoke admin privileges- Disable user accounts- Maintain audit trail
Visible only to:- Developer- Program Office Admin

8. Access Change Workflow
Users can request role changes.Program Office Admin validates and approves.All changes must:
Be auditable
Log previous role
Log new role
Log timestamp
Log approving authority

9. Backend Enforcement Rules
Role resolved at login.
Course-level mapping applied for Faculty, TA, Coordinators.
Tile visibility returned by backend.
API-level RBAC mandatory.
No frontend-only role logic.
Permission changes reflected on next session refresh.
